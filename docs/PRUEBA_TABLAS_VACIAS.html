2. Preparación

  1. Se mantuvieron los esquemas y las tablas que necesita Hibernate para validar las entidades.
  2. Se eliminaron todos los INSERT de los scripts H2 cargados por el perfil Compose.
  3. Se eliminaron los cuatro CSV de la ejecución anterior para no confundir archivos antiguos con el resultado actual.
  4. Se reinició el stack completo con docker compose up -d.
  5. Se esperó a que Kafka, Schema Registry, Kafka UI e Item35 alcanzaran el estado healthy.

5. Por qué C y D generan datos

ITEM35C e ITEM35D no obtienen sus medidas de las tablas H2 anteriores. Sus repositorios consultan Cloudera. En el perfil local application-compose.yml, las tres integraciones están desactivadas: 

component-config:
  cloudera:
    cpu:
      enabled: false
    ram:
      enabled: false
    storage:
      enabled: false

Las anotaciones @ConditionalOnProperty(... havingValue = "false") activan entonces las implementaciones mock. Estas leen los siguientes recursos incluidos en el JAR:

  • ITEM35C: json/total_all_MBT.json y json/free_all_MBT.json.
  • ITEM35D CPU: json/capacity-cpu.json.
  • ITEM35D RAM: json/capacity-ram.json y json/capacity-ram-total.json.

Por tanto, vaciar las tablas afecta a A y B, pero no deja sin datos a C y D mientras Compose continúe utilizando esos mocks. En un entorno conectado a Cloudera, C y D dependerán de las respuestas reales de sus APIs.

6. Conclusión

La prueba confirma que el comportamiento actual no es producir cuatro CSV vacíos. Con las tablas funcionales vacías, ITEM35A e ITEM35B no crean archivo. ITEM35C e ITEM35D sí crean archivos con datos porque el entorno local utiliza respuestas JSON mock independientes de las tablas.

Al finalizar la prueba, el stack quedó iniciado y saludable. Kafka UI permanece disponible en http://localhost:9080 y el endpoint de salud de Item35 en http://localhost:9040/actuator/health.
