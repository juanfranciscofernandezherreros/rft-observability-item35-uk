Cambio propuesto para generar CSV vacíos

Diferencias entre el comportamiento actual y el comportamiento requerido para ITEM35C e ITEM35D cuando Cloudera no devuelve información.

Fecha y hora: 2 de septiembre de 2026, 08:50:52 CEST Zona horaria: Europe/Madrid (UTC+02:00) Documento: cambio técnico

1. Estado del cambio

Prueba con tablas vacías: realizada Se vaciaron las fuentes H2 y se ejecutaron simultáneamente los cuatro reportes.
Generación de CSV vacíos: no aplicada En esta solicitud se documenta el cambio necesario; no se ha modificado todavía el código Java.

Esta distinción evita afirmar que el microservicio ya crea archivos vacíos. Actualmente, cuando una fuente devuelve cero registros, los casos de uso finalizan sin generar el fichero.

2. Qué se cambió para la prueba

  1. Se mantuvieron todos los esquemas y tablas requeridos por las entidades JPA.
  2. Se arrancaron las bases H2 sin los INSERT de datos iniciales.
  3. Se eliminaron los CSV anteriores antes de lanzar la prueba.
  4. Se iniciaron Kafka, Schema Registry, Kafka UI e Item35 con Docker Compose.
  5. Se publicaron a la vez los cuatro tipos de reporte en rft.dev.observability.item.private.v1.

El resultado fue que ITEM35A e ITEM35B no crearon archivo. ITEM35C e ITEM35D sí lo crearon porque el perfil Compose obtiene sus datos de recursos JSON mock de Cloudera.

4. Cambio necesario

Para generar un CSV válido sin registros, pero conservando su cabecera, se debe permitir que los casos de uso invoquen al escritor con una lista vacía.

ITEM35C

En UseCaseStorageCapacity, sustituir los retornos anticipados por un flujo que construya una colección vacía y llame a writeFileStorageCapacityService.writeFile(...). El estado del reporte debe registrarse como completado sin datos, no como error técnico.

ITEM35D

En UseCaseComputeCapacity, cuando CPU o RAM no aporten datos, construir recordsCapacity sin elementos y llamar a writeFileComputeCapacity.writeFile(...). También debe evitarse marcar como error una ausencia de datos que sea funcionalmente válida.

Escritores CSV

No es necesario modificar WriteFileStorageCapacity ni WriteFileComputeCapacity para obtener un fichero con cabecera. Los dos ya escriben primero la cabecera y después recorren la colección: 

writeHeader(csvWriter);

for (Dato dato : lista) {
    writeRecord(csvWriter, dato);
}

Si la lista está vacía, el bucle no escribe registros y el resultado contiene exactamente una línea: la cabecera.

Definición utilizada: “CSV vacío” significa un CSV válido con cabecera y cero filas de datos. No significa un archivo de 0 bytes.

6. Qué no se debe cambiar

  • No se deben inventar ni duplicar registros.
  • No se deben modificar las tablas ni sus consultas para simular información.
  • No se deben conservar los datos de los JSON mock si el objetivo de la prueba es una respuesta vacía de Cloudera.
  • No se debe confundir “sin datos” con un fallo de conectividad, deserialización o escritura.
Para probar este comportamiento, los JSON mock de almacenamiento, CPU y RAM deben devolver colecciones vacías. Vaciar únicamente las tablas H2 no afecta a ITEM35C ni a ITEM35D.

7. Pruebas que acompañarán al cambio

  1. Test unitario de ITEM35C con las dos respuestas de capacidad vacías.
  2. Test unitario de ITEM35D con CPU y RAM vacías.
  3. Verificación de que cada escritor recibe una lista vacía.
  4. Verificación de que cada archivo existe y contiene una única línea de cabecera.
  5. Ejecución conjunta de los cuatro mensajes mediante Kafka.
  6. Comprobación de que los estados finales no se registran como error por una ausencia funcional de datos.
